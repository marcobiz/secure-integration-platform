# M5.5 — Direct Gateway Access coupling audit

**Baseline:** `8774c252b233456173c3ab31346fb21390fb8d7d` (`m5-admin-ui-baseline-20260807`)

**Scope:** identify assumptions that prevent an authorized machine client from using the
Gateway without a Local Broker. This audit precedes product changes and deliberately avoids
cosmetic or destructive renames.

## Classification

### A — genuinely Broker-specific and retained

| Surface | Finding | Decision |
|---|---|---|
| `src/Broker/**` | Windows Service identity, Named Pipe, application-process policy, DPAPI/CNG storage and the production Gateway invoker are Local Broker responsibilities. | Keep Broker-specific. Direct clients do not install or simulate these components. |
| `ProductionGatewayInvoker` | Generates the non-exportable Windows CNG key, persists Broker enrollment state and consumes `/v1/broker-policy`. | Keep unchanged for the Broker path. |
| `/v1/broker-policy` and `BrokerPolicy` | Returns Broker compatibility and protocol policy. | Keep as a compatibility route and reject a Direct installation at this Broker-only endpoint. |
| `ApplicationRecord.MinimumBrokerVersion` / `MaximumBrokerVersion` | Existing Broker product compatibility policy. | Preserve for Broker installations; do not reinterpret it as a universal direct-client constraint. |
| `InstallationRecord.BrokerVersion` | Evidence of the enrolled Broker version used by existing operations and UI. | Preserve for Broker records and wire compatibility. Direct records use an additive generic client-version field. |
| ADR-0017 | MSI, service identity, non-exportable CNG key and Broker repair/upgrade semantics. | Remains applicable only to Broker installations. |

### B — generic Installation concepts with historical naming

| Surface | Finding | Decision |
|---|---|---|
| Installation, credential, activation, locator, grant and replay tables | Models a registry-bound machine identity, not a Windows process or Broker implementation. | Reuse for both kinds; add only an Installation discriminator. |
| `InstallationEnrollmentService` | Challenge, one-time activation, ClientAuth certificate, ECDSA P-256 PoP, renewal and revocation are caller-neutral. | Reuse unchanged in security semantics; generalize version handling. |
| BGW1 envelope | Covers method, canonical target, timestamp, nonce and content digest. It carries no Broker-only field. | Keep BGW1 and the existing routes. No BGW2 and no client migration. |
| `RuntimeIdentityService` | Registry-backed mTLS, signature validation, timestamp and replay checks are caller-neutral. | Reuse as the single inbound authentication adapter. |
| `RegisteredInstallationIdentity` | Tenant/Application/Environment/credential are derived server-side for any machine installation. | Add Installation kind and feed a provider-neutral principal. |
| `InstallationGrantRecord`, `PublishedConnectorAccessContext` and Connector Runtime | Depend only on Installation/Tenant/Application/operation identifiers. | Reuse without a parallel Direct runtime. |
| Admin Installation routes | Operate on generic installation IDs, activation and revocation despite historical UI wording. | Extend additively with `installationKind`; existing omitted values remain Broker. |

### C — coupling that blocks Direct Gateway Access

| Surface | Blocking assumption | Minimal remediation |
|---|---|---|
| Domain/persistence | No `InstallationKind`; every Installation is implicitly a Broker. | Add `Broker`/`Direct`, default existing rows to `Broker`, and add a constrained `client_version` column after migration `0010`. |
| Activation wire/service | `ActivationRequest` accepts only `BrokerVersion`; registry applies Broker compatibility to all activations. | Preserve `brokerVersion` for old clients, add optional `clientVersion`, select the field from the server-owned Installation kind, and apply Broker bounds only to Broker installations. |
| Runtime principal | `AuthenticatedInstallation` contains only the registry record and correlation ID and does not state caller kind or authentication method. | Replace the convergence type with `GatewayClientPrincipal`, exposing server-derived IDs, kind, credential identity, authentication method and security context. |
| Runtime audit | `actorType=installation` does not distinguish Broker from Direct. | Keep the common actor type and add server-derived `callerKind=Broker|Direct`; apply the same metadata to authentication and invocation audits. |
| Broker policy | The route would currently answer any authenticated Installation. | Require `BrokerInstallation` without changing the route used by existing Brokers. |
| Admin API/UI | Creation has no kind and listing cannot show it. | Add the authoritative enum to the OpenAPI contract, default creation to Broker, and add a minimal Broker/Direct selector and Type column. |
| Tests/sample | All authenticated fixtures implicitly exercise Broker. | Make fixture kind explicit, add dual-path/negative tests and a minimal direct client sample that uses enrollment + BGW1 without Broker assemblies. |

### D — documentation-only coupling

- System context and trust-boundary diagrams show only `Legacy → Broker → Gateway`.
- M2/M3 documents describe BGW1 as the Broker-to-Gateway protocol even though its
  fields are caller-neutral.
- Security text says that the Broker always generates the Installation key; this remains
  true for Broker installations but not for Direct installations.
- Audit descriptions list Installation but not the caller kind.

These statements are updated in the M5.5 architecture documents; historical gate reports
remain immutable evidence of the path tested at that time.

## Design conclusion

M5.5 uses one additive discriminator and one inbound principal. Broker and Direct clients
use the same enrollment cryptography, mTLS, BGW1, replay store, revocation, grant lookup,
Published Connector resolution, provider resolution, restricted egress and audit pipeline.
The convergence point is immediately after `RuntimeIdentityService`; no Direct-specific
Connector Runtime, provider, route family or authorization platform is introduced.
