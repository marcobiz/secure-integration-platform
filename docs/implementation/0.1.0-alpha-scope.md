## Track A — Core `0.1.0-alpha`

### Objective

Publish a developer alpha that an external .NET integrator can start from a clean
clone, configure and use in non-production software by following one golden path:

```text
Direct .NET
→ Gateway
→ Connector REST Published
→ Synthetic Provider
→ mock HTTPS/mTLS
→ sanitized response and metadata-only audit
```

The release remains provider-neutral. It does not depend on FSE2 or vendor-specific packs and does not
promise stable API compatibility, MSI, COM/C ABI, Azure live, HA/DR or production.

### Included scope

| Area | Included in TARGET `0.1.0-alpha` |
|---|---|
| Core | Modular-monolith Gateway, PostgreSQL 18 and migrations, Connector Runtime/SDK and provider-neutral contracts. |
| Provider | Synthetic Provider in the supported, repeatable path. |
| Admin | Same-origin Admin API/Web, with DevelopmentAuth only locally and OIDC for complete deployments. |
| Application access | Direct Gateway and .NET client/sample with enrollment, mTLS, BGW1, replay protection, revocation and grants. |
| Connector | One synthetic Published REST Connector, with endpoint and credential bindings resolved server-side and API key + mTLS. |
| Minimum operability | Compose/quickstart, health/readiness, redacted logs, cleanup, checksums, SPDX SBOM and release notes. |
| Core sources | The Local Broker remains in the Core source tree, but MSI and legacy adapters are not part of the supported golden path. |

The canonical Connector is
[`sample-secure-service.connector.json`](../connectors/examples/sample-secure-service.connector.json).
Tutorial, quickstart and adoption proof must use the same example and names.

### Out of scope

- Local Broker MSI and install/repair/upgrade/uninstall;
- C ABI, COM, CLI compatibility, x86/x64 and commercial adapters;
- live-qualified Azure Deployment Pack, AWS, HashiCorp or other cloud providers;
- FSE2 in the Core golden path, real healthcare data and FSE2 production qualification;
- marketplace, billing, HA/DR, multi-region and SLA;
- fuzzing, load/performance and pentest as phase claims;
- regional ePrescription while profiles remain `BLOCKED_BY_SPEC`;
- API stability before a subsequent versioning decision.

### Capability and activation boundary

The Local PKCS12 pack exposes client-certificate use, public material and bounded signing; it does not
expose generic secret retrieval. `SecretValues=false` and the generic-secret slot remains
deny-only. The pack must not acquire `GetSecret` to make enrollment possible.

If the exact real configuration requires `ActivationHmacSecretReference`, the solution is
a separate server-owned capability in composition or an explicit deployment
blocker. Generic secret retrieval is not reopened in the certificate pack, and the secret is not exposed
to the Connector, Broker, client or Admin UI.

### Mandatory qualification order

1. **External intake:** distinguish and separately verify test access and
   applicable software accreditation.
2. **Import/custody preflight:** work outside Git, with verified paths/ACLs/identity and
   no sensitive values in output.
3. **Composition:** compose the required server-owned capabilities, including any
   separate activation HMAC.
4. **Offline cryptographic preflight:** verify public metadata, chain, S1 signing and A1
   mTLS without contacting FSE2.
5. **Warning mapping:** reduce warnings required for `validate-cda` to bounded/allowlisted
   technical codes, discarding raw text.
6. **Vertical deployment:** fix the vertical image, Connector/bindings and exact
   OfficialTest configuration.
7. **Synthetic E2E:** run from the same image and configuration against the synthetic
   server, with pre-network negatives.
8. **`validate-cda` OfficialTest:** use only an authorized synthetic dataset and
   redacted evidence.
9. **`attachment_hash`:** compute it over the exact file bytes supplied as input.
10. **Create/replace:** run them only if authorized by the test plan.
11. **Status:** map only bounded/redacted technical outcomes.
12. **Subsequent workflows:** run them only when included in the authorized plan.
