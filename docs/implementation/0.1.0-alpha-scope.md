# `0.1.0-alpha` — scope e gate di uscita

Stato CURRENT: **scope target approvabile; release non pubblicata**
Baseline CURRENT: `eec2fa5556eccc7e8e3b47fc7d7b127bcac1ed9e`

Questo documento governa le due sole track attive. Non autorizza nuove capability Core,
nuovi verticali o una qualifica production.

## Track A — Core `0.1.0-alpha`

### Obiettivo

Pubblicare una developer alpha che un integratore .NET esterno possa avviare da clean
clone, configurare e usare in un software non-production seguendo un solo golden path:

```text
Direct .NET
→ Gateway
→ Connector REST Published
→ Synthetic Provider
→ mock HTTPS/mTLS
→ risposta sanificata e audit metadata-only
```

La release resta provider-neutral. Non dipende da FSE2 o da pack vendor-specific e non
promette compatibilità API stabile, MSI, COM/C ABI, Azure live, HA/DR o production.

### Scope incluso

| Area | Incluso nel TARGET `0.1.0-alpha` |
|---|---|
| Core | Gateway modular monolith, PostgreSQL 18 e migrazioni, Connector Runtime/SDK e contratti provider-neutral. |
| Provider | Synthetic Provider nel percorso supportato e ripetibile. |
| Admin | Admin API/Web same-origin, con DevelopmentAuth soltanto locale e OIDC per deployment completi. |
| Accesso applicativo | Direct Gateway e client/sample .NET con enrollment, mTLS, BGW1, replay protection, revoca e grant. |
| Connector | Un solo Connector REST sintetico Published, con endpoint e credential binding risolti server-side e API key + mTLS. |
| Operabilità minima | Compose/quickstart, health/readiness, log redatti, cleanup, checksum, SBOM SPDX e release notes. |
| Sorgenti Core | Il Local Broker resta nel source tree Core, ma MSI e adapter legacy non fanno parte del golden path supportato. |

Il Connector canonico è
[`sample-secure-service.connector.json`](../connectors/examples/sample-secure-service.connector.json).
Tutorial, quickstart e prova di adozione devono usare lo stesso esempio e gli stessi nomi.

### Fuori scope

- MSI e install/repair/upgrade/uninstall del Local Broker;
- C ABI, COM, CLI compatibility, x86/x64 e adapter commerciali;
- Azure Deployment Pack live-qualified, AWS, HashiCorp o altri provider cloud;
- FSE2 nel golden path Core, dati sanitari reali e qualifica FSE2 production;
- marketplace, billing, HA/DR, multi-region e SLA;
- fuzzing, load/performance e pentest come claim della fase;
- ePrescription regionale finché i profili restano `BLOCKED_BY_SPEC`;
- stabilità delle API prima di una successiva decisione di versioning.

   unico percorso alpha se non esiste ancora un package feed.
5. Admin Web con la stessa versione prodotto.
6. SBOM SPDX e vulnerability inventory per ogni artefatto distribuito.
7. Core export con inventario/allowlist/hash/byte coverage e digest normalizzato
   riproducibile separato dal manifest evidence della singola run.

## Track B — FSE2 Organization OfficialTest

### Obiettivo e confine CURRENT

Primo TARGET: `validate-cda` nell'ambiente ufficiale di test usando un dataset sintetico
autorizzato. `attachment_hash`, create/replace e status vengono dopo; non sono presentati
come prerequisiti tecnici di `validate-cda` senza nuova evidenza ufficiale.

PR #33 ha integrato e qualificato sinteticamente:

- provider Local PKCS12 opzionale e importer offline;
- immagine verticale contenente `Healthcare.FSE2` e overlay Compose opt-in;
- provider-active synthetic lab;
- firma S1 `contentCommitment` e identità mTLS A1 distinta;
- CI exact-main e security micro-review sul perimetro sintetico.

L'immagine Gateway Core predefinita continua a non includere `Healthcare.FSE2`; soltanto
l'immagine verticale opzionale lo include. Il Core non dipende dal pack.

Non sono ancora avvenuti:

- accesso o import operativo del materiale reale;
- verifica della custody reale;
- configurazione exact OfficialTest;
- chiamata FSE2 o `validate-cda` live;
- accreditamento software attestato;
- create/replace/status live;
- qualifica production.

### Boundary di capability e activation

Il pack Local PKCS12 espone certificato client, materiale pubblico e firma bounded; non
espone generic secret retrieval. `SecretValues=false` e lo slot generic secret resta
deny-only. Il pack non deve acquisire `GetSecret` per rendere possibile l'enrollment.

Se l'exact configurazione reale richiede `ActivationHmacSecretReference`, la soluzione è
una capability server-owned separata nella composition oppure un blocker esplicito di
deployment. Non si riapre generic secret retrieval nel pack certificati e non si espone
il secret al Connector, al Broker, al client o all'Admin UI.

### Ordine vincolante di qualifica

1. **Intake esterno:** distinguere e verificare separatamente accesso test e
   accreditamento software applicabile.
2. **Import/custody preflight:** lavorare fuori Git, con path/ACL/identity verificati e
   nessun valore sensibile in output.
3. **Composition:** comporre le capability server-owned richieste, inclusa l'eventuale
   activation HMAC separata.
4. **Preflight crittografico offline:** verificare public metadata, chain, firma S1 e A1
   mTLS senza contattare FSE2.
5. **Warning mapping:** ridurre i warning necessari a `validate-cda` a codici tecnici
   bounded/allowlisted, scartando il testo raw.
6. **Vertical deployment:** fissare immagine verticale, Connector/binding e configurazione
   exact OfficialTest.
7. **E2E sintetico:** eseguire dalla medesima immagine e configurazione contro il server
   sintetico, con negativi pre-network.
8. **`validate-cda` OfficialTest:** usare soltanto un dataset sintetico autorizzato ed
   evidence redatta.
9. **`attachment_hash`:** calcolarlo sugli exact file bytes forniti in input.
10. **Create/replace:** eseguirli soltanto se autorizzati dal piano di test.
11. **Status:** mappare esclusivamente outcome tecnici bounded/redatti.
12. **Workflow successivi:** eseguirli soltanto quando previsti dal piano autorizzato.

| ID | Condizione verificabile | Claim abilitata |

| FSE2-T01 | Accesso test, accreditamento software applicabile e piano autorizzato sono distinti e verificati fuori Git. | Intake pronto; non production. |
| FSE2-T02 | Custody/import preflight e capability composition provano S1/public chain/`contentCommitment`, A1 mTLS distinta, disable/diagnostica e activation server-owned se richiesta. | Preflight offline; non chiamata live. |
| FSE2-T03 | Exact vertical image/configuration OfficialTest completa E2E sintetico dalla stessa immagine, warning mapping bounded e negativi zero-network. | Deployment candidate; non OfficialTest PASS. |
| FSE2-T04 | `validate-cda` OfficialTest completa end-to-end con dataset sintetico autorizzato, risposta sanificata e audit/evidence redatti. | `validate-cda` official-test qualified sull'exact configuration. |
| FSE2-T05 | Per workflow successivi autorizzati, hash usa exact file bytes; create/replace e status bounded completano con limiti di durata espliciti. | Solo gli specifici workflow attestati; non 11/11 impliciti. |

Il primo risultato può essere dichiarato **`validate-cda` qualified for the official FSE2
test environment on the attested configuration** soltanto dopo FSE2-T01..T04 e T06.
La claim create/status richiede anche FSE2-T05. Nessuna delle due implica production,
Human Actor, durata cross-process, accreditamento di altri soggetti o qualifica live di
tutte le 11 operation.
